1. PURPOSE AND OBJECTIVE

This proposal covers technical consultancy for bringing the existing
NeuralConstraints/Gecode solver core to a stable form for use in Beethoven AI.
Dr. Vassallo will act primarily as technical advisor and solver specialist to
the project's graduate developer and software team. He will also implement or
correct parts of the core where his specialist knowledge is required.

The main output is a documented, compiled C++ solver core with a stable input
and output interface. The imec/project software team will embed this core in the
larger Beethoven AI system. Previously completed and university-funded research,
architecture, and prototype work are not charged under this proposal.


2. EXISTING FRAMEWORK

NeuralConstraints/Gecode is a C++17 polyphonic music-generation framework built
on Gecode and informed by the rule-based, multi-voice approach of Cluster
Engine. It represents pitch, rhythm, meter, harmony, and voice relationships as
musical constraints. Gecode guarantees that returned solutions satisfy the hard
rules, while heuristic and neural components can guide the search toward more
appropriate musical results without overriding those rules.

The existing core accepts structured JSON specifications, supports configurable
search limits and deterministic seeds, and returns score data for downstream
use. This assignment therefore concerns advice, focused development, and
production hardening of an existing system rather than a new implementation.


3. SCOPE OF WORK AND DELIVERABLES

Dr. Vassallo's role will combine regular technical guidance with focused work on
the parts of the solver that require his knowledge of its architecture and
musical constraint model.

3.1 Music generation and orchestration

- Advise the graduate developer on translating the artistic requirements into
  pitch, rhythm, harmony, meter, voice-leading, and orchestration constraints.
- Review production configurations and implement difficult core constraints or
  search behavior where necessary.
- Support the initial workflow in which Theme 1, Theme 2, and Filler material is
  selected from the sketch archive and reused across the concert.

3.2 Runtime reliability

- Review and improve solver behavior for repeated generation, unsatisfiable
  inputs, timeouts, deterministic reproduction, and error reporting.
- Profile and optimize the core where tests identify a material bottleneck.
- Advise on practical fallback behavior for rehearsals and performance.

3.3 Integration support and intermediate releases

- Agree a small, versioned JSON input/output contract with the imec software
  team and provide example requests and results.
- Deliver intermediate compiled core builds so integration can proceed before
  the complete musical rule set is finalized.
- Support generation of several selected blocks in one preparation cycle. Each
  block will carry stable identity and ordering metadata so the surrounding
  system can stitch the results before sending the score to the orchestra.
- Diagnose solver-side integration issues and advise the software team during
  embedding.

3.4 Testing and rehearsals

- Review tests written by the graduate developer and add focused regression
  tests for critical solver behavior.
- Evaluate musical and technical results with IPEM, Kit Armstrong, Jan Caeyers,
  and the software team as appropriate.
- Provide remote support around the planned 27 September and 15-17 October 2026
  test opportunities, subject to confirmation and availability.
- Refine the core in response to agreed rehearsal findings throughout the
  consultancy period.

3.5 Final delivery and documentation

- Deliver the agreed compiled solver core for embedding by the software team.
- Provide concise interface, build, configuration, and troubleshooting notes.
- Conduct a technical handover with the graduate developer and software team.

The imec/project software team remains responsible for embedding the compiled
core into the broader system, application-level score stitching, user
interfaces, networking, deployment of that broader system, and delivery of
scores to the orchestra.


4. ACCEPTANCE BASIS

Acceptance will use test cases agreed with the software and musical teams. The
compiled core must satisfy enabled hard constraints, handle agreed error and
timeout cases safely, support Theme 1, Theme 2, Filler, and ordered multi-block
requests, and be invokable by the software team using the supplied examples.
Runtime targets will be agreed once the target hardware and integration method
are known.


5. EXCLUDED SCOPE

Material scope changes require written approval and a separate estimate.
